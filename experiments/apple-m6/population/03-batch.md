## Contract findings that constrain every candidate

1. **The existing C batch function is already single pass.** Baseline `HdrHistogram_c/src/hdr_histogram.c:829–860` computes ranks into the destination and walks one iterator for all ordered targets. Its complexity is already O(scanned counters + outputs). A direct/blocked scan removes per-counter work; it does not introduce the O(N + K) algorithm for the first time. The O(KN) comparison applies to repeated singular calls, a separate usage comparison.

2. **C batch and singular outputs are not universally interchangeable.** The rank expression and its operation order are at candidate `src/hdr_histogram.c:840–845`; batch always returns the highest equivalent value at a crossing (`877`, `887`, `900`). Singular p0 uses the lowest (`816–826`). Valid empty batch leaves each initialized target at 1. Coarse empty histograms need not give singular value 0 for positive percentiles. Preserve null argument `EINVAL`, including length zero, and leave a valid zero-length output untouched (`831–845`). The header's `ENOMEM` statement is stale (`include/hdr/hdr_histogram.h:275–285`), not permission to change error behavior.

3. **The candidate's empty-path comment is incorrect, although its shortcut preserves results for valid empty state.** At `src/hdr_histogram.c:848–851`, the comment says the iterator never advances on empty input. `hdr_iter_init` actually selects `all_values_iter_next` (`1059–1073`), which calls `move_next` (`1047–1056`) and stops at `counts_len` (`988–998`). The baseline therefore traverses the dense array on empty input. Only `basic_iter_next` uses the total-count test; it is not selected here. Measure the empty shortcut separately from the flat blocked scan. This is also a metadata assumption: total_count==0 must mean all counters are zero for the shortcut to preserve baseline output.

4. **Valid removals and negative bins are different cases.** `hdr_record_values` accepts a signed count and does not check its sign or the resulting bin (`534–552`); the header does not explicitly state a nonnegative-bin precondition (`130–139`). Removing 5,000 from a bin holding 10,000 is compatible with block skipping, and the harness covers that (`batch_bench.c:113–118`). Removing more than a bin holds can produce nonmonotone cumulative counts. The candidate changes baseline signed accumulation to unsigned even in the supposedly unchanged offset fallback (`853`, `897–898`). Unsigned arithmetic prevents signed overflow in that addition; it does not preserve signed-prefix comparison semantics.

   Shared evidence from the root review, not executed by this reviewer: ASan/UBSan probes of baseline/candidate batch p50 report `16:+2, 20:-2, 48:+2` (total 2) returning 16/48; `20:-2, 48:+4` (total 2) returning 48/20; and `16:+2, 20:-2` (total 0) returning 16/1. Every recording call accepted its update and no sanitizer error occurred. The fixture is `experiments/apple-m6/population/semantic_probe.c`. These respectively expose block skipping across a declining prefix, unsigned-prefix comparison, and the empty shortcut. They establish observed compatibility differences on public-record-accepted states; they do not establish mathematical percentile correctness for negative populations or a novel upstream bug. Valid removals preserving nonnegative bins remain a separate case.

5. **Positive percentiles plus nonempty input do not establish singular equivalence for every extreme count.** Under ordinary IEEE round-to-nearest, total_count=2^53+3 and p100 produce target=2^53+4, which exceeds the actual total. Baseline batch leaves that unresolved target in the output; singular falls through its count scan and decodes value 0 (`711–826`). The current equivalent-work benchmark is safe for its small totals, but its comment at `batch_bench.c:130–131` is too broad. Existing large-count checks stop at 3*2^50 (`105–108`), below this example. Near INT64_MAX, the floating-to-integer conversion itself can leave the representable range; that pre-existing undefined behavior must be separated from well-defined rank-rounding tests. Keep the exact rank expression; no fast-math, reassociation, saturation, or target-to-total clamp under an optimization label.

6. **The oracle has a narrower domain than the baseline.** `batch_reference` stops when cumulative count reaches total_count (`batch_bench.c:18`), while the baseline iterator walks all counters until outputs resolve. That shortcut is valid for nonnegative consistent histograms but cannot prove arbitrary signed-state parity. Tests for accepted negative-bin behavior need a literal baseline/iterator oracle without that cutoff. Rotating only `normalizing_index_offset` in the existing harness is a useful valid normalized-view test; add fixtures that physically rotate counters while preserving the same logical histogram when evaluating a new normalized traversal.

## B1 — finish the existing flat blocked8 candidate

**Anchors.** `.tools/m6-batch/src/hdr_histogram.c:829–905`, particularly empty shortcut `848–851`, reduction/skip `857–870`, crossing replay `872–880`, tail `882–890`, and normalized fallback `892–903`. The unchanged iterator overhead is visible in the same candidate file at `988–1008`: `move_next` performs bucket value, lower/upper/median equivalent calculations for every visited counter. Queued runner: `experiments/apple-m6/run_batch.sh:5–29`; comparison loops: `batch_bench.c:125–219`.

**Mechanism and potential.** High potential on long, flat-storage scans relative to the iterator baseline: decode values only at requested crossings, and test one subtotal per eight counters. Confidence in the removed work is high; confidence in an M6 performance win is medium until measured. Empty input has a distinct likely substantial saving from O(counts_len) traversal to O(length) target initialization. It cannot validate the blocking mechanism.

**Counterargument and risks.** Short/early scans pay the block reduction and replay. The replay loop continues to the end of its eight-counter block after the final target resolves. Frequent crossings or duplicate ranks can make decoding/output work dominate. The normalized fallback retains iterator costs and changes signed arithmetic. Historical x86 gains for the cached upstream branch are not M6 evidence. A batch-vs-singular win alone does not establish a candidate-vs-baseline win.

**Minimal isolated experiment.** Once cleanup is confirmed and correctness scope is explicit, run unchanged `1fe058d` versus unchanged `8c4cdcc` with identical O2/compiler settings using the queued runner. Keep singular candidate `df89e1f` out of both libraries. Declare nonempty flat spread length 7/32 as the main target before seeing results; report length 1 and tiny/empty individually. Preserve separate baseline-vs-candidate and within-binary batch-vs-equivalent-singular ratios, both in ns per group. The existing length 1/7/32 matrix is the first decision, not a complete acceptance matrix.

**Falsification and controls.** Add to subsequent supplemental coverage, without editing immutable referees: significant figures 1–5; early/middle/late crossings; one-bin and spread populations; all-equal ranks, repeated ranks from distinct percentiles, and no-duplicate ranks; p0/p100; valid removals including removal to zero; offsets 0, +/-1, +/-(counts_len-1); and the well-defined 2^53 boundary example. Retain target outputs for unresolved ranks. Reject the proposed nonempty scan benefit if paired results do not support it, or if the only gain comes from empty input. Use assembly/profile evidence to check removal of iterator decoding and actual reduction code generation. If attribution remains unclear, a later flat-scalar ablation from the cached single-pass branch can distinguish iterator removal from blocking; do not accumulate it before completing this comparison.

**Contract gate.** Existing validation supports nonnegative consistent states, including valid removals, not every state accepted by the recording function. Establish and document that scope before accepting a broad compatibility claim; otherwise use a baseline-equivalent implementation for the additional signed states. Rejecting negative record arguments is a separate API/write-path change and would also reject valid removals. Do not hide it inside B1.

## B2 — decode once for all targets crossed by one bin

**Anchors.** Candidate crossing/tail/fallback assignments at `src/hdr_histogram.c:875–878`, `885–888`, `898–901`. A local pattern exists in `.tools/m6-batch/src/hdr_packed_histogram.c:664–670` and `675–680`: compute a value once, then emit it for all reached targets. Cached Go `hdrhistogram-go/hdr.go:559–580` also demonstrates holding the next target and terminating once complete, but has different public semantics.

**Mechanism and potential.** Moderate potential for length 32 on tiny or highly concentrated populations, duplicate percentiles, and distinct percentiles rounded to the same rank/bin. Confidence is medium: all outputs reached at the current index share one highest-equivalent value, so a single decode can feed them. This is a small, allocation-free refinement with favorable benefit per complexity if generated code currently repeats the decode.

**Counterargument and risks.** The compiler may already eliminate repeated decode work. Length 1 or a batch with one crossing per distinct bin offers little or no benefit; long scans may remain reduction-bound. A new branch around the emit group can cost more than it saves. Output/target storage is shared, so every next target must be consumed before its slot is overwritten; avoid an out-of-bounds reload after the final output. Do not turn this into sorting, target compression requiring allocation, a length cap, or singular dispatch.

**Minimal isolated experiment.** Only after B1 is measured, inspect its optimized crossing loop. If repeated decoding remains, replace just the decode-per-output operation with decode-once-per-crossed-bin at the three emit sites, keeping block width, rank preparation, numeric representation, and empty/fallback dispatch unchanged. Compare against the same fixed B1 revision. A cached-next-target rewrite or final-output immediate return is a separate follow-up, not part of this first delta.

**Falsification and controls.** Test lengths 1/7/32 with all targets in one bin, two duplicate groups, all unique crossing bins, and high/low-percentile selections. Include p0 in the semantic tests: it still gets the batch's highest equivalent value. Include unresolved final targets and positive/negative valid offsets. Falsify the mechanism if assembly already decoded once, or if concentrated batches do not improve. Unique-crossing and length-1 groups plus ordinary write/singular referees are the regression controls. This candidate preserves the existing batch output contract within B1's stated state domain; it does not repair B1's wider signed-state gap.

## B3 — normalized scan as two contiguous scalar spans

**Anchors.** Candidate `src/hdr_histogram.c:892–903` uses the iterator for every nonzero offset; `normalize_index` at `53–73` maps logical index i to i-offset with one wrap. Logical value decoding is `hdr_value_at_index` at `246–258`; iterator field overhead is at `988–1008`.

**Mechanism and potential.** For a valid bounded nonzero offset, derive the physical start for logical index 0, then visit counts[start..n) followed by counts[0..start), preserving a separate increasing logical index for value conversion. A direct scalar traversal removes normalization and iterator field updates per counter. Potential is high for long rotated scans compared with the fallback, but overall benefit and confidence are low-to-medium because the current timed batch matrix never exercises nonzero offsets. Complexity is moderate, so this ranks below B1/B2.

**Counterargument and risks.** Flat histograms get no direct benefit. Duplicated span control can increase code size; off-by-one wrap errors return plausible but wrong values. Blocks crossing the physical boundary would require careful tails, so do not introduce them in the first experiment. Invalid decoded offsets remain the decoder's separate validation concern. Preserve the existing fallback arithmetic for the stated domain; if claiming baseline signed-state compatibility, use signed per-counter comparisons and validate that separately, without claiming it repairs B1's flat path.

**Minimal isolated experiment.** First establish representative demand for rotated percentile queries. Add only a normalized direct scalar two-span fallback to the measured B1 version, keeping its flat path unchanged and using no SIMD or persistent metadata. Compare identical physical rotations of the same logical data against B1's iterator path at lengths 1/7/32. Do not use a physical index as a histogram value index.

**Falsification and controls.** Crossings immediately before/at/after wrap, span lengths 1/7/8/9, all offsets already exercised by the validator, empty histograms, repeated ranks, p0/p100, large counts, and valid removals are required. Test physically rotated storage against an unrotated logical twin and the independent normalized oracle. Falsify if benefit is absent in nonzero-offset workloads or if flat controls regress. Broaden to blocked spans only if scalar measurements justify it; that is not included in B3.

## API-changing ideas excluded from this optimization population

- Sorting arbitrary C inputs, rejecting an out-of-order request, allocating a map, deduplicating away outputs, or returning an iterator would change or extend the existing ordered-array contract. Do not import them from the Rust/Go APIs. Cached Rust `src/lib.rs:1407–1456` also uses ceil-based ranks, zero for empty input, and low-equivalent p0, unlike C batch. Go `hdr.go:522–579` preserves arbitrary input order through allocation/sorting and uses different empty/p0 behavior. Packed C sorts targets and allocates above 32 (`hdr_packed_histogram.c:614–645`); that is not the dense API's contract or allocation profile.
- Dispatching every length-1 batch to public singular is not a drop-in optimization: p0, empty, and well-defined unresolved large-count ranks differ. Clamping ranks to total_count or returning hdr_max for p100 would change the latter behavior too.
- Binary search needs monotone cumulative counts, not raw count cells. Building a fresh prefix array adds work and storage to a one-pass query; maintaining one persistently changes writes, invalidation, memory, and potentially ABI. The plan explicitly defers persistent indexes. No such candidate is warranted here.

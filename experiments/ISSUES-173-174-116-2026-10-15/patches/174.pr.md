## What

`hdr_value_at_percentiles` writes each percentile's cumulative-count target into `values[]` and uses it as scratch space during the scan. If the scan never reaches a target, that internal value stays in the slot and is returned. This happens in two cases:

- **Empty histogram.** Every slot came back as `1`. That is the clamped rank target, not a value.
- **Counts summing below `total_count`.** This happens if the struct was written directly, or read while writers were still recording. The upper slots returned raw rank targets, e.g. `2` or `4`.

This PR adds a short fill loop after the scan, outside all three scan paths (block, tail and offset-aware iterator). Each unresolved slot gets exactly what `hdr_value_at_percentile` returns for that percentile when its own scan finds nothing: the not-found value `0`, run through the same boundary rule.

```c
values[i] = percentiles[i] == 0.0 ? lowest_equivalent_value(h, 0) : highest_equivalent_value(h, 0);
```

## Why

The batch API should never expose its scratch state, and it should agree with the singular API. After this change, for every slot and every configuration, these three agree:
- dense plural
- dense singular
- packed plural (`hdr_packed_value_at_percentiles` already fills unresolved slots this way)

For example, an empty histogram with `lowest_discernible_value = 100` gives `0` at p0 and `63` (the top of bucket 0) at p > 0, in all three APIs.

## Compatibility

- Return codes are unchanged.
- The only values that change are slots that used to hold leaked internal rank targets, which were never meaningful.
- With `lowest_discernible_value == 1`, unresolved slots are now `0`.
- This PR does not decide what an empty histogram *should* report. It only makes the batch API match the current singular contract. A separate change can move the empty-histogram contract to `0` across all APIs.
- The fill uses the same exact `percentiles[i] == 0.0` rule as the singular API. That keeps it consistent with any later change to p0 handling in the batch scan.
- Doc fix: the header said `ENOMEM` for a null destination array. The code has always returned `EINVAL` when `percentiles` or `values` is null. The header now also says that unresolved percentiles get the same value as `hdr_value_at_percentile`.

## Tests

New tests in `test/hdr_histogram_test.c`:
- **`test_value_at_percentiles_empty`** runs for lowest 1 and 100, using percentiles {0, 50, 99.9, 100, 150} and a `-7` sentinel buffer. It checks batch == singular for every slot in four cases:
  - a fresh histogram;
  - `normalizing_index_offset != 0` (the iterator path);
  - a buffer reused from a non-empty call, after `hdr_reset`;
  - `length == 0`, which must write nothing.
- **`test_value_at_percentiles_unresolved_targets`** uses lowest 100, offset 0 and 37, one recorded value, and `total_count = 4`. p25 resolves to the recorded value; the higher percentiles are unresolved. It checks batch == singular for every slot.

New test in `test/hdr_packed_histogram_test.c`:
- **`test_plural_empty_parity`** uses an empty histogram with lowest 100. It checks dense plural == packed plural for every slot, p0 == 0 and p50 == 63.

All new tests fail on current main and pass with the fix. The tests were built with `-Wall -Wextra -Wshadow -Winit-self -Wpedantic -Wmissing-prototypes` and gave no warnings. They pass under ASan and UBSan.
